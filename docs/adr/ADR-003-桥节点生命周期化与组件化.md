# ADR-003：ROS2 桥节点生命周期化，并以组件形式进容器

- **状态**：Accepted（2026-09-29。注意："决策已定并落码"与"已验证"是两件事——
  最后一节的实测数字待 VM 跑完回填，缺数字不等于已验证）
- **相关**：`ros2/dmp_ros2_bridge/{include/dmp_ros2_bridge/bridge_node.hpp,src/bridge_node.cpp,
  src/bridge_main.cpp,src/bridge_component.cpp,CMakeLists.txt}`、
  `ros2/dmp_ros2_bridge/launch/dmp_bridge.launch.py`、`launch/dmp_bridge_composed.launch.py`、
  `tools/vm_lifecycle_compose.sh`、`docs/adr/ADR-001`、`docs/adr/ADR-002`、
  `docs/经典Bug素材录.md`（B-01 / B-15 与本决策直接相关）

## 背景

ADR-001/002 之后，桥是一个普通 `rclcpp::Node`：进程一起来就连网关、起定时器、发话题。
两个问题在真机链路与机队规模下暴露出来：

1. **"采集开没开"没有权威答案。** 运维/上位机只能靠"话题上有没有数据"反推。而本项目已经两次
   栽在"节点在、话题在、不报错、零数据"这一类故障上（B-01 的 `select(0)`、QoS 错配、B-15 的
   服务名写错）—— 用"有没有数据"当判据，恰好是这些故障最擅长伪装的样子。
2. **一台设备 = 一个进程。** 每台桥都有一份 DDS 参与者、一份发现协议开销。机队到几十台时，
   这笔开销是线性的，而桥的实际算力需求极低（解码 + 转发）。

ROS2 对这两件事各有一个标准答案：`LifecycleNode`（把"就绪/采集/停采"变成可查询的状态机）和
component composition（把 N 个节点装进一个进程）。

## 决策

**A. 就地升级成 `LifecycleNode`，副作用严格按状态分配**（不留一份普通节点并行维护）

| 阶段 | 做什么 | 明确不做什么 |
|---|---|---|
| 构造器 | 只有基类初始化 | 不读参数、不连网关、不建话题 |
| `on_configure` | 声明并**校验**参数；建两个回调组、三个 publisher、三个 service；读一次 RULES | 不 publish；不因"网关还没起来"而失败 |
| `on_activate` | 建四个定时器；立刻 `publishRules()` + `tickLink()` | —— |
| `on_deactivate` | 先停定时器，再关网关连接，清空跨周期缓冲 | 不销毁拓扑（话题仍在，仍可问状态） |
| `on_cleanup` | 释放 publisher/service/回调组，计数与解码器归零 | —— |

**B. 不 autostart**（节点自己绝不激活），但 launch 层提供显式可选的自动链
`autostart:=true`（默认）用事件处理器实现；`autostart:=false` 留给负例测试。

**C. 三个 service 在 `configure` 创建并按当前状态应答**，`set_rule` 额外加生命周期守卫。

**D. 数据面与控制面分两个 `MutuallyExclusive` 回调组**（`grpData_` / `grpCtl_`），
并提供组合容器 launch，用 `mt:=true/false` 在多线程/单线程容器间切换。

## 理由与权衡

- **B 的代价是真实的**：忘了 `activate` 就零数据，症状与 B-01 完全同族。接受它的理由是
  "误激活/漏激活"至少变成**一行命令可查询**的东西（`ros2 lifecycle get`），并且验收脚本里
  configure/activate 是显式一步 + 一句状态断言，而不是靠 `echo` 有没有输出反推。
  把风险从"不可观测"换成"可观测且可断言"，这是本项目的判断标准。
- **C 选 configure 而不是 activate**：运维在**停采状态**下更需要问"你现在什么状态、当前阈值是什么"。
  若服务只在 activate 存在，未激活时外部得到的是 B-15 那句 `waiting for service to become available`
  的沉默——用"沉默"表达"我在但没激活"是最坏的表达方式。于是 `selftest` 的应答里带 `state=`，
  未激活时 `healthy=false`；`get_rules` 不加守卫（读操作不该被状态机挡住）；`set_rule` 加守卫，
  `reason` 里回显 `state=`。
- **configure 只对"配置本身不合法"返回 FAILURE**（周期非正、端口 0、`frame_qos` 名字不认识）。
  "网关还没起来"是 WARN + 交给 `tickLink`/`tickRules` 重试。如果把时序问题返回成 FAILURE，
  整个 launch 会因为启动顺序而失败，运维看到的字样是"配置错误"——伪装出来的因果关系最难查。
  `frame_qos` 未知值直接拒而不是退化成 `sensor`：静默退化会精确地把订阅端送进"零数据且不报错"。
- **activate 里立刻 `publishRules()` + `tickLink()`**：否则规则话题要等第一个 `rule_refresh_ms`（默认 10s）、
  数据面连接要等第一个 `link_check_ms` 才动，验收脚本会在"其实一切正常"的头几秒里误判成没数据。
- **D 的分组不是风格**。控制面一次 `RULES` 回读要等约 80ms 的静默期且同步阻塞；单线程容器里这段
  时间会把**同容器其他设备**的帧发布一起卡住（头阻塞）。所以两个回调组必须配多线程容器才有意义
  （两个组喂给单线程容器 = 白写），这也正是 `mt:=false` 这一路存在的目的：**留一个能复现故障的开关，
  比留一句"我们考虑过并发"的注释值钱**。
- **OBJECT 库**：`src/bridge_node.cpp` 只编一次，独立进程与组件插件共用。既不是为了"两份节点实现"
  （那等于两份契约，一定会漂移），也不是把节点做成 `SHARED` 再让 exe 去链接（那会引入安装后
  RPATH/`LD_LIBRARY_PATH` 问题，现象是 `ros2 run` 直接 rc=127，错误信息只有一句
  `error while loading shared libraries`）。

## 被否决的替代方案

- **并存一份普通 Node + 一份 LifecycleNode**：两份实现两份契约。否决。
- **在构造器里直接 `configure()+activate()`（伪 autostart）**：`/transition_event` 上不会留下真实
  转换记录，等于把"是否采集"重新变回不可查询。否决。
- **引入 `lifecycle_manager` 做自动激活**：VM 的 Humble 里**该包未安装**（实测），且它会再加一层
  进程与参数面。launch 事件处理器就够，且转换是从 launch 里发出去的真实 `ChangeState` 事件。否决。
- **`OnStateTransition` 只写 `goal_state='inactive'`**：`deactivate` 也落回 `inactive`，事件处理器会
  把它再次激活——现场形态就是"运维按下停止，三秒后设备自己开始采集"。必须限定
  `start_state='configuring'`，只认"配置中→闲置"这一条边。否决。
- **组合容器也用 launch 事件处理器自动激活**：Humble 的 `ChangeState` 靠 `lifecycle_node_matcher`
  匹配 launch 内的 **`LifecycleNode` action**，而组合节点是容器自己 `dlopen` 出来的，launch 层没有
  对应 action 可匹配；`ComposableNode` 也没有生命周期参数。于是组合场景的状态转换只能由外部驱动
  （`ros2 lifecycle set`）。**刻意不用 `ExecuteProcess` 在 launch 里补这一层**：那会把"谁在驱动状态机"
  藏进 launch 文件，反而更难排查。
- **`rclcpp::spin(node)`**：编译不过去——它只接受 `rclcpp::Node`。改为
  `SingleThreadedExecutor` + `exec.add_node(node->get_node_base_interface())`。

## 事实清单（全部在 VM 上探针核实，不靠记忆）

- `LifecycleNode : public node_interfaces::LifecycleNodeInterface` → 派生类**作用域内**裸名
  `CallbackReturn` 可解析（定义在 `lifecycle_node_interface.hpp:50`，是 `enum class : uint8_t`）。
  但有两个编译期细节只有真编一次才知道（本轮两条真实错误）：
  ① `.cpp` 里的**类外定义**不能裸写 `CallbackReturn DmpBridgeNode::on_configure(...)` ——
     返回类型出现在 `DmpBridgeNode::` 之前，那时查找还在名字空间作用域，基类嵌套类型看不见
     → 在 `namespace dmpbr {}` 里加一行 `using CallbackReturn = ...::LifecycleNodeInterface::CallbackReturn;`；
  ② `LifecycleNode::get_current_state()` 在 Humble **不是 const 成员**（后来版本才改），
     所以 `isActive() const` / `stateLabel() const` 会得到两行 `discards qualifiers` → 只能跟基类一起不带 const。
- `LifecycleNode::create_service(...)` 返回 `rclcpp::Service<ServiceT>::SharedPtr`，第 4 个形参是
  `rclcpp::CallbackGroup::SharedPtr group = nullptr`。
- `create_publisher` 返回 `rclcpp_lifecycle::LifecyclePublisher<T>`；其 `publish()` 未激活时
  **静默丢弃**，且 `should_log_` 在首次激活前为 false——连一句 warn 都没有。
- `create_wall_timer(period, cb, group)` 在 `LifecycleNode` 上可用。
- 探针能钉死**接口存在与签名**，钉不死**名字可见性与 const 正确性**：上面两条都是探针全绿、
  真编仍错。所以“零猜测”的边界是“不猜 API”，不是“不编译”。
- `launch_ros.LifecycleNode` 在 Humble **没有** `autostart` 形参（只有 `name/namespace/**kwargs`）。
- `lifecycle_manager` 包未安装；`rclcpp_components` 提供 `component_container` /
  `component_container_mt` / `component_container_isolated`。
- `rclcpp_components_register_node(target)` 的 `PLUGIN` 与 `EXECUTABLE` **都是必填**；
  `EXECUTOR` 默认 `SingleThreadedExecutor`。
- `component_container_mt` 不解析 `--help`（实测：把它当 ROS 参数直接起容器），所以线程数用
  `MultiThreadedExecutor` 默认值（`number_of_threads = 0` → 硬件并发数）。
- `launch_ros` 的模块名是 `descriptions`（`from launch_ros.descriptors import ...` 会 ModuleNotFoundError）。
- `perform_substitutions(context, subs)` 的第二形参要的是 Substitution **列表**。

## 影响与验证条件

- 兼容性影响（已随之修改）：`tools/vm_e2e.sh`、`tools/vm_qos_mismatch.sh` 必须显式
  `configure`+`activate`；`tools/vm_realdevice_e2e.sh` 加了一句状态断言。
  `frame_qos` 参数从"未知值静默退化"变成"拒绝 configure"——这是一次**行为收紧**，
  写在这里就是为了让人能找到它。
- 断言证据（`tools/vm_lifecycle_compose.sh`，逐项 PASS/FAIL，不靠人眼看日志）：
  unconfigured 时 `/dmp/frames` 不在 topic list、自研服务不在 service list、
  但 `/dmp_bridge_bed01/change_state` 必须在；inactive 时话题/服务都在但 6s 采样 0 批、
  `set_rule` 被拒且 `reason` 带 `state=inactive`、`get_rules` 仍可读；active 后恢复；
  `deactivate` 再次 0 批；`cleanup` 后话题从 ROS 图上消失（这是 `on_cleanup` 真的释放了
  publisher 的唯一外部证据，只打一行日志不算）。
- 实测证据（头阻塞 A/B）：同一容器两台设备，对 bed01 连打 `set_rule`（服务端要做同步的网关
  `RULES` 多行回读），只测 bed02 的 `/dmp/frames` 到达间隔，`mt` 与 `st` 各一遍。

  判读口径：`st` 的"打满"列应显著大于其空载基线（≈`batch_period_ms`=50），`mt` 两列接近。
