## 1. 软件描述

- **软件名称/预期用途**：多仪器数据采集与监控上位机软件（DeviceMonitorPlatform），用于连接检验/监护类设备，实时显示测量值、越限时产生危急值告警并存储历史记录。（个人作品集/技术演示，**不用于真实临床诊断**）
- **软件功能**：设备接入、数据采集/解析、实时显示、阈值告警、历史存储与回放、导出、后端服务化（文本 API / gRPC）、运维诊断归因。
- **接口**：下位机 UART(TCP 模拟或真串口)/帧协议见 `frame_protocol.h`；数据库 SQLite；北向 gRPC `proto/telemetry.proto` 与文本行网关 `service_proto.h`。
- **部署/运行环境**：Windows 10/11 + MinGW（Qt 6.10.0 mingw_64）；Linux/WSL2 Ubuntu 22.04（gRPC 服务侧）；嵌入式目标 STM32F103（HAL）。
- **开发框架/过程模型**：自研 V 模型（需求→架构→单元设计→单元/集成/系统验证），文档与代码同仓演进，自动化回归由 GitHub Actions 承担（详 §3/§6/§9）。
- **是否 SaMD / SiMD**：含 **SiMD** 边界（`firmware/` 为器械嵌入式软件一部分，与器械协同运行）与 **SaMD** 边界（上位机/网关/gRPC/Agent 为独立数据处理软件）；本项目作为能力展示同时讲清两侧接口如何以帧协议契约隔离。

## 2. 软件安全分级（IEC 62304 5.1）

> 分级依据：软件失效是否可能导致伤害。A=无伤害；B=非严重伤害；C=死亡/严重伤害。

| 软件项/模块 | 危害分析 | 安全等级 | 说明 |
|---|---|:--:|---|
| 帧解析 / 数据链路 | 丢帧/错值 → 误读测量 | B | 数据完整性失效可能导致错误判断 |
| 危急值告警 | 告警漏报/延迟 → 延误处置 | C | 安全关键，最高级 |
| 数据显示 UI | 显示错误 → 误判 | B | |
| 历史存储 | 记录丢失 → 追溯缺失 | B | 影响不良事件回查，非直接伤害 |
| 运维诊断 Agent | 误诊建议误导运维 | A | 只读网关 STATS/ALARMS/HISTORY，输出仅作运维参考、**不进入任何控制回路**，失效不直接致伤害，故定最低级 |

- 安全等级 A 可免完整生命周期控制；B 需 5.3/5.6/5.7/5.8（部分）；C 需 5.3/5.6/5.7/5.8（增强）+ 7.3。
  本项目实际裁剪与其理由已集中记录于 **§3 策划末尾**（一句话：保留追溯/验证/风险三项做实，省略独立 QA 与生产/退市过程）。

## 5. 架构与详细设计（5.4 / 5.5）

- **分层**：L1 设备层（`firmware/` STM32 固件 或 `device_simulator`）→ L2 采集协议层（`frame_protocol.h` 解帧 / `ring_buffer.h` 无锁缓冲 / `acquisition.h` 告警与 Sink 抽象 / `pipeline.h` 线程化）→ L3 消费与服务层（`qt_monitor.cpp` UI、`storage.h` CSV/SQLite、`gateway_service.cpp` 文本 API、`service/grpc_server.cpp` gRPC）→ L4 运维智能（`tools/dmp_agent.py`）。（见 architecture.md）
- **单元划分与关键接口**（每个头文件即一个可独立编译/测试的单元）：

| 单元 | 对外接口（契约） | 安全等级 | 验证 |
|---|---|:--:|---|
| `frame_protocol.h` | `encodeFrame(Sample)→bytes`；`FrameDecoder::feed(bytes, cb)` 流式解帧 | B | test_protocol 27 |
| `ring_buffer.h` | `RingBuffer<T,N>::push/pop`（SPSC 无锁，满则 false+计数） | B | test_protocol（含 10 万元素并发） |
| `acquisition.h` | `pushBytes()`/`drain()`/`stat()`/`setSink()`/`setAlarmCallback()` | C | test_protocol / test_storage |
| `pipeline.h` | `ProducerThread<Source>::start/stop` + 原子统计快照 | B | test_pipeline 9 |
| `storage.h` | `CsvSink::open/onSample/flush`；`loadCsv()`；`TeeSink::add()` | B | test_storage 35 |
| `service_proto.h` | `parseCommand(line)→Command`；`format*()` 纯函数 | B | test_service_proto 25 |
| `firmware/dmp_frame_core.c` | `dmp_build_frame()`/`dmp_crc16_ccitt()`（纯 C，PC/MCU 同源） | B | test_frame_parity 41 |

- **跨端一致性设计**：固件与上位机共用同一帧内核，`test_frame_parity` 以“逐字节相等 + 交叉解帧 + 金标准帧”锁定契约，杜绝协议漂移（→ R-002）。
- **传输可替换性**：业务层只依赖 `Acquisition`；文本行网关与 gRPC 服务是同语义的两种传输实现，客户端可插拔（→ SR-008/SR-010）。
- 对于 B/C 类：单元全绿后再做集成测试（TCP/串口端到端、真机→gRPC 全链路），再进系统级验收，见 §6。

【示例】单元测试用例：
- `FrameDecoder`：粘包（2 帧连发）、拆包（半帧分两次）、噪声前缀、CRC 错帧重同步 → 断言 ok/crcErr。
- `RingBuffer`：满时 push 返回 false 且 dropped 计数正确；SPSC 并发无数据竞争。
- 告警规则：心率 120 触发、70 不触发；边界值 50/110 判定。

> **【已实现并通过 ✅】** `tests/test_protocol.cpp`（自带极简断言宏，无三方依赖）**27 项断言全绿**，覆盖：单帧编解码往返、粘包（两帧连发）、拆包（一帧分两次）、噪声前缀帧头重同步、CRC 错帧丢弃并恢复后续、环形缓冲满丢弃/空弹出/计数、SPSC 10 万元素多线程不丢不重、采集端到端解码+阈值告警。
> 构建运行：`g++ -std=c++17 -pthread -Iinclude tests/test_protocol.cpp -o test_protocol && ./test_protocol`（或 `ctest`）。
> 另：`monitor_console` ↔ `device_simulator` 已做端到端冒烟（TCP 收帧→解码→告警），实测量 ok 递增、crcErr=0、drop=0。
> **存储层（SR-004）**：`tests/test_storage.cpp` **35 项断言全绿**——CSV 写入/读回一致、表头仅写一次、多次追加不重复、坏行容错、TeeSink 扇出、帧→解码→采集→CSV→回放 确定性集成。
> **协议一致性（SR-006）**：`tests/test_frame_parity.cpp` **41 项断言全绿**——MCU 固件侧纯 C 内核 `firmware/dmp_frame_core.c` 与上位机 `include/dmp/frame_protocol.h` 编/解码 **逐字节相等**（相同 CRC-16/CCITT-FALSE、浮点/seq 小端布局），含交叉解帧（固件帧→上位机流式解码）与金标准帧回归锚点。
> **真实硬件链路（SR-005）**：下位机 `firmware/dmp_frame.{h,c}` 经 STM32 USART1 发帧，上位机 `src/monitor_serial.cpp` 裸串口（CreateFile/ReadFile）收帧解码；**已真机实机验收**——命令行刷录(Verify OK)，`serial_check.ps1` 实测 raw/ok 同步增长、四路体征解码、crcErr 恒 0；刷录过程中曾由 Agent 归因反推出固件采样计数相位锁死 bug（改用心率专用计数修正）。
> **Qt6 上位机**：`src/qt_monitor.cpp`（滚动曲线/告警/SQLite/TCP+串口）已用 Qt 自带 cmake+Ninja+MinGW13.1 **编译+链接通过**；`--verify` 无头自检 **PASS（N=50：解码=drain=落库=曲线 四方计数一致, crcErr=0）**，并已接入真机串口一键连接（`run_qt_serial.ps1 --demo-serial COM4`）。过程中修掉一个构造函数 `status_` 未初始化即解引用的空指针崩溃。
> **多线程采集（SR-007）**：`include/dmp/pipeline.h` `ProducerThread` 将阻塞读源置于独立线程，主线程周期消费，统计量以原子快照发布（严守 SPSC 所有权，规避数据竞争）；`tests/test_pipeline.cpp` **9 项断言全绿**（N=5000 帧、每块 7 字节跨线程不丢不重不乱序 + 析构可 join）。
> **服务层（SR-008）**：`include/dmp/service_proto.h` 命令解析/格式化纯函数 + `tests/test_service_proto.cpp` **25 项断言全绿**（parseCommand 各分支/默认值回退/Unknown.name、RAW与HISTORY 解析、format* 逐字节比对）；`src/gateway_service.cpp` TCP 网关（含 `--serial` 串口上游与 RAW 逐字节透传）**端到端实跑** ✅。
> **真机→gRPC 全链路（SR-010）与运维 Agent（SR-011）**：`e2e_realdevice.sh` 实跑 `ok=34 crc_err=0 dropped=0` + 10 条真机样本 seq 递增；`tools/dmp_agent.py` 在真机数据上完成告警归因（见 §10）。

> **CI 化过程中暴露并修复的 3 个真实可移植性缺陷（回归证据）**：
> ① `CMakeLists.txt` 仅声明 `LANGUAGES CXX`，CMake **静默跳过** `firmware/dmp_frame_core.c` → Linux 链接期 `undefined reference to dmp_crc16_ccitt`（Windows 用 g++ 手编时 `.c` 被当 C++ 处理因而隐蔽）→ 改为 `LANGUAGES C CXX`；
> ② `gateway_service.cpp` POSIX 分支缺 `<arpa/inet.h>`，`inet_addr` 未声明 → 补包含；
> ③ `test_storage.cpp` 写死相对路径 `build/_storage_test.csv`，无该子目录时 `fopen` 返回 `nullptr` 仍直接 `fprintf` → **段错误** → 改用当前工作目录并对空句柄/空容器加守卫。
>
> 【面试话术】“我把项目挂上 CI 后，第一跑就红了——它揭发了三个只在 Linux 侧才会暴露的真 bug：其中一个是 CMake 静默没编译固件 C 内核，意味着我们的‘协议一致性 41 断言’在另一套工具链上其实从未真正跑过。”

## 7. 确认（Validation）

- **裁剪依据**：本项目为个人作品集/技术演示，**不用于真实临床、不进入任何器械控制回路**，故不执行“预期用途下的临床用户确认”；该边界与 §2 将 Agent 定为 A 类、告警链路仅为演示注入同源。
- **等效确认证据**（以三类真实使用场景端到端跑通代替临床确认）：
  1. Qt GUI 直连真机串口——实时曲线可见、越限弹横幅+声、可人工确认；
  2. 真机→网关→gRPC→网络客户端全链路（`e2e_realdevice.sh`：ok=34 / crc_err=0 / 10 条样本 seq 递增）；
  3. 自然语言提问由运维 Agent 给出带数字支撑的归因结论（基线/峰值/阈值带）。
- **验证与确认的区分口径**：*验证*(Verification) 回答“东西做对了吗”→ 137 断言 + CI 门禁；*确认*(Validation) 回答“做对东西了吗”→ 上述三场景。两者证据分存，不互相冒充。

## 8. 风险管理（ISO 14971 摘要）

| 风险ID | 危害 | 可预见事件 | 危害情况 | 严重度(S) | 概率(P) | 风险评价 | 控制措施（→可追溯验证项） | 残余风险 |
|---|---|---|---|:--:|:--:|:--:|---|:--:|
| R-001 | 危急值漏报 | 网络丢包/解析错帧/告警链路阻塞 | 延误处置 | 高 | 低 | 中·ALARP 可接受 | CRC-16 + 帧头重同步 + 有界告警环 + 阈值判定单测（SR-001/003/008） | 可接受 |
| R-002 | 数据错值 | 字节序/浮点布局/固件与上位机协议漂移 | 误读测量 | 中 | 低 | 低 | 逐字节一致性测试 SR-006（41 断言）+ 协议回归 | 可接受 |
| R-003 | UI 冻结/丢帧 | 采集阻塞 UI 线程、突发洪峰 | 无法及时观察 | 中 | 中 | 中·可接受 | 采集/UI 线程分离 SR-007（ProducerThread）+ 无锁 SPSC 环形缓冲 SR-002 | 可接受 |
| R-004 | 历史丢失 | 掉电/未落库 | 追溯缺失 | 低 | 中 | 低 | 批量落库 + SQLite（SR-004，`--verify` db_rows=N 校写入计数） | 可接受 |
| R-005 | 服务链路丢字节 | RAW 透传截断、gRPC 流断连、WSL↔Windows 网络抖动 | 下游解码错/数据不达 | 中 | 低 | 低 | 上游连入即订 RAW + 逐字节透传不重组 + 全链路 probe 实测 crc_err=0 dropped=0（SR-010） | 可接受 |
| R-006 | Agent 误诊 | 窗口样本不足、阈值带判读错 | 误导运维（非临床） | 低 | 中 | 低 | 结论必附数字证据(crc_err/峰值/均值)；只读、不进控制回路；离线确定性模式结果可复现（SR-011） | 可接受 |

- **剩余风险评价**：上述每项控制均落到具体可验证条目（见第 10 节），并以 137 项断言 + 真机串口验收 + 真机→gRPC 全链路 + Agent 端到端实跑为客观证据；无一项残余风险超出可接受界，不需额外防护/警示。
- **收益-风险分析**：收益在于把设备数据采集/告警/追溯流程标准化并法规化；已识别风险均有对应工程控制与验证覆盖，综合收益大于剩余风险。
- **生产与生产后信息（PMCF）**：现场以网关 `STATS`（ok/crc_err/dropped）作为链路健康度在线监测指标，异常即回归至 R-001/R-005 复评（本项目为个人招牌，按此口径演练）。

## 9. 配置管理 / 维护 / 停产（5.1 之外 & 12 章）

- **基线与命名**：语义化版本 `主.次.修`；源码以 Git 为唯一基线，`.gitignore` 排除 `build*/`、`*.log`、`*.o/*.exe`、`*.db*` 与测试 CSV 产物；提交即触发 CI（§6）。
- **构建可复现性**：所有产物可由“源码 + 固定工具链”重建 —— MinGW gcc/g++ 13.1、Qt 6.10.0(mingw_64)、CMake ≥ 3.16、Ninja；WSL2 侧 gRPC 依赖由 `wsl_setup.sh` 一键安装（钉在 Ubuntu 22.04 apt 仓库）。仓库内不提交二进制；`firmware/dmp_frame_core.c` 与上位机同源，天然不存在“固件/上位机版本不同步”。
- **变更影响分析（实际执行的规则）**：
  - 改动 `frame_protocol.h` 或 `dmp_frame_core.c` → 视为**协议变更**：必须同步更新 `test_frame_parity` 金标准帧并重跑真机链路（影响 SR-001/005/006/010，风险 R-002）。
  - 改动 `service_proto.h` 命令表 → 必须同步网关实现、Agent 工具集与 HELP 文本断言（影响 SR-008/011）。
  - 改动告警阈值 → 需重评 §2 安全分级与 §8 R-001，并补边界值用例。
- **缺陷分类与处理时限（口径）**：Critical=漏告警/数据错值 → 当日修复并回归；Major=链路断/丢帧 → 3 日内；Minor=显示与文案 → 下个迭代。
- **维护与停产**：作品集期内持续维护；停出口径为归档仓库并在 README 顶部标注“不再维护”；因无真实用户，不执行现场通知/退市过程。
